### YOUR TASK

1. **Select.** Include every finding the Grounder marked **CHECK** or **RELOCATE**. Exclude every **DROP**. For a RELOCATE, use the corrected file/line the Grounder recorded, not the one in the original finding.
2. **Do not re-litigate.** Trust the Grounder's dispositions. Do not revive a DROP, and do not add findings no reviewer raised.
3. **State the observation plainly and end on the substance.** Describe what is in the code directly and factually: "the sort omits the region identifier", "the merge key is not unique in either dataset", "the lagged variable is built from the wrong column". These are observations about what is written, not accusations, so they need no softening. End each item on what matters: what the code does and what in the paper it appears to differ from ("this appears to differ from the definition on p. 12"). Where the consequence is an inference rather than something on the page, hedge the inference itself ("which would weight units by their number of observations"), not the observation. Do NOT stamp a check-formula onto items — a list where every paragraph ends "worth confirming…" / "worth checking…" / "worth reviewing to ensure…" reads as machine output. An explicit check clause is fine where it names a specific thing to confirm that the observation alone does not, in a minority of items, never with repeated phrasing.
   - **Courtesy formulas are BANNED as padding.** "The author may wish to…", "the author might want to…", "the author should verify…", "it would be helpful/useful to…" — do not open items with these, and never use more than one such phrase in the entire output. The deferential register is carried by the items being checks; it does not need restating in every sentence.
   - BANNED as statements of fact: "the code is wrong", "this produces the wrong result", "running this fails", "this is an error". Never write these even when the finding feels certain. If it were certain, it would still be written as a check here.
   - **No runtime predictions, hedged or not.** Nobody ran this code, so you do not know what happens when it executes. Never predict execution behaviour: "will halt", "may halt", "would error", "could crash", "fails to run", "may interrupt the script" are all banned. Adding "may" or "could" to a runtime prediction does not turn it into a check; it is still a claim nobody tested. When an upstream finding predicts that code halts or errors, drop the prediction and keep the structural observation — state what is written where and what looks inconsistent (e.g. the commands that save the results sit outside the loop that creates the variables they use), then ask the author to confirm that section runs and behaves as intended.
4. **Order by consequence.** Lead with items that bear on a primary or headline result. Group items confined to an appendix exhibit, a robustness check, plotting cosmetics, or a typo together at the end. Convey weight through ordering and plain description — do **not** attach severity labels. Never write "this is a critical issue", "major", or "minor".
5. **Write the description.** Base it on the original finding's detail, corrected by the Grounder's location and notes. Keep specific file references, variable names, and function names. If every file path you are given begins with the same top-level folder (a zip wrapper such as `replication_package/`), drop that folder from the paths you write — `data/build.do`, not `replication_package/data/build.do`. Keep the rest of each path intact. You may quote short inline snippets (e.g. `absorb(id year)`) where they aid clarity. Do **not** include fenced multi-line code blocks (``` ``` ```) — these render badly in the final PDF.
6. **Format.** One paragraph per item, starting with a bold label in sentence case. Output the items only — no preamble, no heading, no closing line. Your output is spliced verbatim into the report.
